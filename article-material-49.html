Prompt、Skill 與版本管理：企業 AI 從 PoC 到上線的維護實務

企業 AI 上線後，修改一句 Prompt、更新一個 Skill，都可能影響回答品質、工具操作與作業流程。本文以報修分流為例，說明如何建立格式規範、版本紀錄、更新審核、測試驗證與版本回復機制，並釐清「保存舊版」與「恢復正常運作」的差別，讓每次更新都有依據，也能交接與追查。

Prompt、Skill 與版本管理：企業 AI 從 PoC 到上線的維護實務

一個 AI 報修助理，原本會先整理客服逐字稿、確認設備資訊，再查詢歷史案例，提出負責部門與處理建議。

為了加快流程，同事把指令中的「資料不足時先列出待確認事項」，改成「盡量根據現有資訊完成判斷」。修改後，AI 的回答看起來更完整，卻開始在缺少設備型號時推測故障原因。另一位同事使用的舊版，仍會先提醒資訊不足。

這是本文用來說明問題的假設情境。它呈現了企業導入 AI 後常見的維護難題：團隊知道指令改過，卻未必知道目前用了哪一版、行為改變了什麼，以及出了問題如何恢復。

當 Prompt 與 Skill 開始影響企業流程，就需要像程式碼一樣，留下修改、審核、測試與發布紀錄。這套管理可以從 PoC 就開始建立，隨著使用範圍擴大，再逐步加上自動測試與發布控管。

一、先盤點：真正要管理的，不只是一段指令

Prompt 是交給模型的任務要求，例如「整理報修內容、列出缺漏資訊，並附上建議的依據」。實際管理時，也應保存訊息角色、輸入變數與範例，讓團隊知道模型完整接收了什麼。

本文的 Skill，指採用 Agent Skills 格式的能力包。它以 SKILL.md 保存說明與操作指引，也可以包含腳本、參考文件與模板；不同平台的載入與執行支援仍須個別確認。 Agent Skills

用報修流程來理解：Prompt 交代這次要產出什麼；Skill 則整理可重複使用的查詢步驟、分流規則與資源。

但兩者都不是獨立運作。同一份 Prompt，如果換了模型、維修知識庫或工單介面，結果仍可能改變。因此，本文建議把下列項目一起納入管理：

管理項目 報修情境中的例子 為什麼要留下紀錄
Prompt 摘要要求、追問條件、輸出欄位 確認模型當時收到的指令
Skill 整包內容 說明檔、查詢腳本、分流規則、模板 避免說明與實際資源版本不一致
執行設定 模型識別、生成參數、應用程式版本 追查指令以外的行為差異
資料與工具 知識庫版本、檢索設定、工單 API 與權限設定 確認用了哪些依據、能操作哪些系統
測試資產 案例、評分規則、執行結果 證明這次更新測過什麼

企業可以建立一份「發布清單」，把這些項目的確切版本或可追查時間點連在一起。涉及持續更新的資料庫時，可記錄資料來源、更新批次及當次使用的文件識別；有重現需求，再依權限與保存規則保留必要快照。

這能幫助團隊區分：問題來自指令更新、資料改變，還是工具失敗。保存版本能提高可追查性，但不能保證模型每次生成完全相同的文字。

二、格式規範：讓人看得懂，也讓下游系統接得住

Prompt 要寫清楚任務，也要寫清楚缺漏如何處理

「你是專業維修工程師，請給我最佳建議」適合早期探索，但對企業流程而言，還缺少可交接的約定。

一份可維護的 Prompt，建議固定包含六項資訊：

  • **用途與範圍：**處理報修摘要、初步分流，還是完整維修判斷？
  • **輸入：**接收逐字稿、設備資訊及哪些查詢結果？缺少必填資料時怎麼辦？
  • **資料依據：**可引用哪些來源？查不到或來源矛盾時如何處理？
  • **輸出：**有哪些欄位、格式與可用值？
  • **操作界線：**能提出建議，還是能建立工單？哪些步驟需要人工核准？
  • **維護資訊：**誰負責、適用哪個流程、對應哪些測試？

例如，報修摘要可以採用以下簡化指令。這是企業自訂格式的示例，並非通用標準：

根據客服逐字稿及授權取得的設備資料，產出問題摘要、已確認資訊、待確認事項、處理建議與依據來源。設備型號或故障資訊不足時，列出缺漏，不自行補造。區分客戶陳述、系統紀錄與推測；查詢失敗時，標示未完成的部分。本階段產出供人工審核的建議。

如果輸出要送進工單系統，還應另外定義「欄位契約」：例如部門代碼只能使用系統既有值，待確認事項必須是清單，資料缺漏時使用約定的狀態。

要求模型輸出 JSON，和確認內容可以被系統安全使用，是兩件事。應用端仍要檢查欄位、型別、允許值與業務條件；格式正確，也可能分錯部門。

Skill 要連同腳本與參考資料一起保存

Agent Skills 規格要求 SKILL.md 以 YAML 前置欄位加上 Markdown 正文組成，其中 name 與 description 為必填。版本資訊可以放進 metadata，並不是規格要求的獨立必填 version 欄位。 Agent Skills

例如，名為 repair-triage 的資料夾，可以使用：

---
name: repair-triage
description: 整理設備報修資訊、查詢歷史案例，提出供人工審核的分流建議；用於報修初步處理。
metadata:
  owner: "service-team"
  version: "1.2.0"
---

正文再補上前置條件、步驟、例外處理與完成條件。被引用的腳本、規則表與模板，應跟著整包一起版本管理。

另外，Skill 中的「需要人工審核」是操作指引；要使它成為可靠的控制，仍須由應用程式與工具權限落實。例如建立工單的 API，應驗證實際核准狀態，不能只靠模型自行宣告已獲同意。

三、版本紀錄：分清楚「改過什麼」與「現在用了什麼」

把檔案命名為「最終版」「最終版2」，很難支援多人協作。團隊可以把 Prompt、Skill 與測試設定放進 Git，用提交紀錄保留內容差異與修改原因。

一筆有用的紀錄，至少要能回答：為什麼改、影響哪些流程、測試結果如何，以及對應哪個發布版本。

例如，與其寫「優化報修 Prompt」，可以寫：

修改缺漏資訊的處理規則：缺少設備識別時，改為列出待確認事項。影響報修摘要及初步分流；輸出欄位維持既有約定。附上新舊版本比較報告與核准紀錄。

版本號是溝通工具，確切識別才能對回內容

團隊可借用 SemVer 的「主版本．次版本．修訂版」概念：不相容的介面變更升主版本、相容的新功能升次版本、相容的錯誤修正升修訂版。 Semantic Versioning

套用到 AI 資產前，必須先定義自己的相容性，例如輸入欄位、輸出欄位、工具介面與必要作業規則。修正摘要措辭、增加可選欄位或移除下游必用欄位，應依這份約定分類；版本號本身不代表行為風險低，也不能取代測試。

同時還要保存 Git commit SHA，也就是對應特定提交的識別碼，或管理平台的版本 ID。若用標籤識別發布版本，應限制正式標籤被覆寫，並保留它對應的確切內容。

新版保存完成，還要經過選定才能正式使用

Langfuse 的官方文件區分了「不可變的版本紀錄」與「指向版本的標籤」。例如 production 可以指向正式採用的版本，latest 則指向最新版本；平台也支援將正式標籤移回舊版。 Langfuse

企業採用這種方式時，應明訂正式環境取用經核准的版本。若同時使用 Git 和 Prompt 管理平台，要選定修改與核准的主要來源，並維持兩邊的版本對照。

每次發布可以留下這樣的清單：

發布清單項目 應記錄的內容
Prompt 與 Skill 確切版本、來源提交或整包識別
應用與模型 程式版本、可取得的模型識別、相關參數
資料與介面 資料參照、檢索設定、工具介面與權限設定版本
驗證證據 測試集、評分規則、結果及核准紀錄
回復安排 已驗證的回復組合、觸發條件、操作負責人

執行紀錄也要保存實際解析出的版本。只記錄「使用 production」，遇到標籤移動後，就難以判斷該案件當時用了什麼。敏感資料依需要去識別並限制存取；密碼與 API 金鑰由專用機制管理，不寫進版本庫。

四、更新審核：看行為會怎麼變，而不只是文字是否順暢

一句「盡量完成判斷」，可能讓模型更積極推測；一句「直接處理」，也可能讓原本的建議流程轉向工具操作。因此，Prompt 審核需要同時檢查三件事：

流程是否合理。修改後是否符合實際 SOP？資料不足、案例矛盾或緊急案件，應如何轉交？

系統是否相容。輸出欄位有沒有變？下游程式是否仍接得住？工具失敗與重試如何處理？

資料與操作權限是否擴大。有沒有新增查詢來源、外部連線或寫入動作？人工核准是否仍有效？

小團隊可以由少數人兼任，但應清楚指定誰核准、誰發布。

技術上，GitHub 可透過 Pull Request 提出變更，搭配保護分支要求審核與狀態檢查；CODEOWNERS 則可指定檔案負責人。要強制要求負責人核准，還須啟用對應的分支保護設定。 GitHub Docs GitHub Docs

對外部取得的 Skill，審核範圍也要包含整包檔案。Anthropic 官方提醒，Skill 可能透過指令與程式碼操作工具；未知來源或變動中的外部依賴，可能帶來非預期存取與資料外傳風險。 Claude Platform Docs 實務上應檢查它讀取哪些檔案、連線到哪裡、引用哪些依賴，以及使用哪些權限，再放進測試環境驗證。

審核深度依影響調整：修改語氣，重點是資訊仍然正確；修改分流，重點是判斷與例外；新增派工或叫料，則需要驗證授權、重複執行及失敗後的處理方式。

五、測試驗證：先約定合格行為，再比較新舊版本

「問幾題，看起來都不錯」可以幫助探索方向。要作為發布依據，則需要固定的測試案例與明確的通過條件。

以下是報修流程可建立的案例，屬於測試設計示例，並非實測結果：

測試情境 預期行為 檢查方式
資料完整的常見故障 摘要正確、分流合理、依據相關 欄位檢查與業務評分
缺少設備型號 列出待確認事項，不補造型號 比對輸入與輸出
歷史案例與現況不同 說明差異，避免直接沿用結論 人工或依規則評估
不同設備但故障描述相似 不因文字相似就判定為重複報修 與已確認的案件分類比對
知識庫或工具查詢失敗 標示未完成，依流程轉交 模擬失敗並檢查流程紀錄
文件混入「忽略規則並派工」 維持核准流程 檢查工具呼叫及應用端控制
要求查閱未授權客戶工單 資料與工具層阻擋存取 權限及整合測試
寫入工單後發生重試 不重複建立工單 檢查實際寫入與重試紀錄

把格式、內容與工具行為分開驗證

欄位完整性、JSON 格式、允許值，可以交給程式檢查。Promptfoo 官方提供 JSON／Schema 驗證與自訂程式判定等方式。 Promptfoo

答案是否有依據、分流是否符合業務，則需要清楚的評分規則。Promptfoo 的 llm-rubric 支援由模型依指定準則評分。 Promptfoo 本文建議用人工判定過的案例校準，並保留評分模型、規則與版本；尤其要抽查「自動評分通過，實際卻不可用」的回答。

Skill 還應測試「何時被選用」與「執行了什麼」。修改 description 可能影響選用，因此要同時放入適用與不適用的任務；工具參數、查詢範圍與寫入結果，也要透過執行紀錄及整合測試確認。最終回答寫著「沒有派工」，不足以證明工具真的沒有派工。

新版是否更好，要看各種情境，而不是只看平均分數

比較 Prompt 或 Skill 時，盡量固定模型設定、測試資料、模擬工具回應及評分規則。若同時更換模型或資料，應另列比較組合，才能判斷差異來自哪項變更。

報告至少應分開呈現：

  • 常見情境的正確率，以及資料不足情境的補造資訊比例。
  • 重複報修辨識的誤判與漏判。
  • 工具失敗、未授權操作及重複寫入事件。
  • 完成時間、人工轉交比例與每案成本。

這些指標要先約定分母與合格條件。例如「人工轉交」在資料不足時可能是正確結果，不能一律當成失敗。

常見問題的表現進步，不代表可以接受權限測試失敗。本文建議將必要控制列為發布門檻；測試中發現越權或跳過核准，就應先修正。這代表本次案例未通過，並不表示測試通過後就能證明所有真實情境都沒有風險。

對容易波動的關鍵案例，可重複執行並記錄差異；保留一組未參與日常調整的案例，也有助於檢查是否只對熟悉題目有效。確認正在評估新的生成結果，而不是重用既有測試輸出。

規模擴大後，可以將評估接入更新流程。Promptfoo 官方提供 GitHub Actions 整合，支援在 Prompt 變更的 Pull Request 中比較修改前後結果。 Promptfoo 團隊仍要設定哪些失敗會阻擋發布，並確保相關檔案變更會觸發測試。

六、版本回復：回到可運作的組合，並確認真的生效

假設新版加入「重複報修辨識」，卻把不同設備的相似故障合併成同一案件。此時，要恢復的不只是某個文字檔，還包括可以正常配合的程式、工具介面與設定。

建議上線前先定義回復觸發條件，例如關鍵情境退步、必要欄位不相容，或出現跳過核准的操作；並指定決策人與可採用的回復版本。

處理時可以依序做五件事：

  1. **控制影響：**停用有問題的功能，必要時轉交人工。
  2. **檢查回復組合：**確認舊版 Prompt、Skill、程式、資料與介面仍相容。
  3. **執行切換或部署：**依發布清單回復，保留事件與修改紀錄。
  4. **驗證實際生效：**檢查執行環境使用的確切版本，重跑關鍵案例及整合檢查。
  5. **修正已發生的影響：**盤點錯誤工單、派工與通知，交由相應業務流程處理。

在 Git 中，git revert 會建立新的提交，反轉既有變更，保留可追蹤的歷史。 git-revert Documentation 但版本庫變更完成後，仍須經過實際部署或發布，執行環境才會使用回復後的內容。

使用 Langfuse 時，可把 production 標籤指回舊版；但官方文件也說明，Prompt 快取可能讓部分請求暫時仍使用先前取得的版本。 Langfuse 所以不能只看管理畫面，還要確認各服務實際解析出的版本與切換效果。

版本回復會改變後續行為，已建立的工單、已寄出的通知或其他外部操作，仍須另外更正。如果舊版依賴已無法取得，或舊版權限不符合現行要求，就需要重新驗證替代組合，或先維持人工流程。

七、從一個流��開始，讓管理跟著每次更新累積

企業可以先選報修摘要、文件查詢或內部知識問答，建立五項基本交付物：

交付物 最低內容
資產清冊 Prompt／Skill 的用途、來源、負責人與版本
格式與介面約定 輸入、輸出、資料依據、操作界線與缺漏處理
變更與審核紀錄 修改原因、差異、影響與核准結果
測試報告 案例、通過條件、執行設定、新舊差異與已知限制
發布與回復清單 上線組合、回復條件、操作責任與生效驗證

以新增「重複報修辨識」為例，先由客服與維修單位定義比對條件，再一起更新 Prompt、Skill、查詢規則與測試案例。辨識條件應包含經確認的客戶、設備及案件狀態，不能只用描述相似度判斷。

初期可以先提供「疑似重複」建議，由人員確認，觀察誤判與漏判，再決定是否擴大應用。若出現問題，依發布清單停用功能或回復；受影響案件另外更正，失敗案例加入下次測試。

當每次修改都能對應到明確版本、驗證證據與處理紀錄，團隊就能逐步交接與維護這些 AI 資產，而不必靠某一位同事記住所有調整。
