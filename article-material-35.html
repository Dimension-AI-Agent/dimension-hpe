企業 AI 與 Agent 實務 · 成效與成本評估

企業如何評估 AI Agent：從任務完成率、穩定性到執行成本

Anthropic 說明 AI Agent 的評估方法，強調驗收應確認任務是否實際完成，並透過重複測試觀察結果的一致性。企業可結合程式檢查、模型評分與人工審查，追蹤任務成功率、延遲、錯誤率與每次任務成本，作為 PoC 驗收及上線後持續改善的依據。此素材適合說明企業如何建立可衡量的導入標準；若要進一步計算投資報酬，仍需補充人工處理基準、建置成本與業務收益。

Anthropic｜Demystifying evals for AI agents（已翻譯成中文）

揭開 AI Agent 評估（Evals）的神秘面紗

發布日期：2026 年 1 月 9 日

AI Agent 的自主性、智慧與彈性讓它們非常有用，但也使評估變得更加困難。有效的 Agent 評估通常需要結合多種方法，才能對應系統本身的複雜程度。

Introduction｜引言

Evals 能讓團隊在問題影響使用者之前，就發現 Agent 的失敗模式與行為變化，避免只能在正式環境中被動除錯。

The structure of an evaluation｜評估的結構

Anthropic 將 Agent Eval 拆成幾個核心元素：

  • Task：單一測試案例
  • Trial：某個 Task 的一次實際執行
  • Grader：判斷 Agent 表現的評分機制
  • Transcript / Trace / Trajectory：完整執行紀錄
  • Outcome：執行結束後環境真正產生的結果
  • Evaluation Harness：負責執行與管理整套 Eval 的基礎設施
  • Agent Harness / Scaffold：讓模型能以 Agent 形式運作的系統
  • Evaluation Suite：針對特定能力建立的一組測試案例

Why build evaluations?｜為什麼要建立 Evals？

早期開發可以依靠人工測試、Dogfooding 與直覺，但 Agent 規模擴大後，缺乏 Evals 會讓團隊難以：

  • 判斷是真正 Regression 還是隨機波動
  • 在發布前大量測試情境
  • 衡量改進是否真的有效
  • 快速評估新模型是否適合升級

How to evaluate AI agents｜如何評估 AI Agent

Types of graders｜Grader 類型

主要分成三類：

  1. Code-based graders

    • 快速、便宜、客觀、可重現
    • 適合測試明確且可程式化驗證的結果

  2. Model-based graders

    • 使用 LLM 評估
    • 適合開放式、自然語言或主觀品質問題
    • 需要與人工評分進行校準

  3. Human graders

    • 品質最高
    • 適合專家判斷與主觀問題
    • 但成本與時間較高

Capability vs. Regression Evals

Capability Eval
檢驗「Agent 現在能做到多難的事情」。

Regression Eval
檢驗「Agent 原本會做的事情，現在是否仍然可靠」。

成熟的 Capability Eval 最後可以轉變成持續執行的 Regression Suite。

Evaluating coding agents｜Coding Agent

Coding Agent 適合大量使用確定性測試，例如：

  • Unit Tests
  • Static Analysis
  • 執行結果
  • 程式碼品質 Rubric

Evaluating conversational agents｜對話型 Agent

除了最終任務是否完成，也必須評估：

  • 對話品質
  • 是否正確使用工具
  • 是否完成目標
  • 對話輪數
  • 語氣與回覆品質

有時還需要第二個 LLM 模擬使用者。

Evaluating research agents｜Research Agent

Research Agent 的品質較難用單一答案衡量，因此可以組合：

  • Groundedness
  • Coverage
  • Source Quality
  • Exact Match
  • LLM Rubric

並定期與領域專家的人工判斷校準。

Computer use agents｜Computer-use Agent

需要讓 Agent 真正在 GUI 或 Sandbox 環境中操作，再確認：

  • UI 狀態
  • 檔案狀態
  • 資料庫狀態
  • Application Configuration
  • 最終操作結果

Non-determinism｜非確定性

Agent 每次執行結果可能不同，因此單次 Pass / Fail 不一定能代表真實能力。

常用：

  • pass@k：k 次嘗試中至少成功一次的機率
  • pass^k：k 次嘗試全部成功的機率

前者偏向衡量「是否有能力找到解法」，後者偏向衡量「是否能穩定成功」。

Going from zero to one｜從零建立 Agent Eval

Anthropic 建議：

Step 0：越早開始越好

初期甚至只需要約 20–50 個來自真實失敗案例的 Task。

Step 1：從現有人工測試開始

將：

  • Release 前人工檢查
  • Bug
  • Support Ticket
  • 使用者失敗案例

轉成 Eval Tasks。

Step 2：建立明確 Task 與 Reference Solution

Task 不應存在模糊條件。

理想情況下，不同領域專家應能獨立得出相同的 Pass / Fail 判斷。

Step 3：保持測試資料平衡

同時測試：

  • 某個行為「應該發生」的案例
  • 某個行為「不應該發生」的案例

避免 Agent 為了提高 Eval 分數而過度觸發某種行為。

Step 4：建立穩定的 Eval Harness

每個 Trial 應盡量：

  • 從乾淨環境開始
  • 彼此隔離
  • 避免共享狀態
  • 接近 Production Agent 的實際環境

Step 5：設計合適的 Graders

原則：

  • 能用 Deterministic Grader 就優先使用
  • 必要時使用 LLM Grader
  • 人工評估作為校準

應優先評估 Agent 最終完成了什麼，而不是強迫 Agent 按固定路徑完成任務。

Step 6：閱讀 Transcript

不能只看分數。

需要閱讀 Agent 的執行軌跡，判斷失敗究竟來自：

  • Agent
  • Grader
  • Task Specification
  • Eval Harness

Step 7：注意 Eval Saturation

當 Capability Eval 接近 100%，它就無法再有效衡量模型進步。

此時需要增加更困難的 Task。

Step 8：長期維護 Eval Suite

Eval Suite 應視為持續維護的工程資產，就像 Unit Tests 一樣。

Anthropic 建議採用 Eval-driven Development：

先用 Eval 定義預期能力，再逐步讓 Agent 達到要求。

Evals 與其他 Agent 評估方法

完整的 Agent 品質評估不應只依靠 Automated Evals，還應搭配：

  • Automated Evals
  • Production Monitoring
  • A/B Testing
  • User Feedback
  • Manual Transcript Review
  • Systematic Human Studies

不同方法就像多層防護機制，各自補足其他方法無法發現的問題。

Conclusion｜結論

Agent Eval 的核心不是建立一個完美的 Benchmark，而是建立持續改進循環：

真實失敗 → Eval Task → 找出問題 → 改善 Agent → 防止 Regression

關鍵原則包括：

  • 儘早開始
  • 使用真實 Task
  • 明確定義成功條件
  • 結合多種 Grader
  • 維持足夠難度
  • 持續改善 Eval 的訊噪比
  • 實際閱讀 Agent Transcript

Appendix: Eval frameworks｜Eval 框架

文章另外介紹數種可使用的 Eval 工具：

  • Harbor
  • Braintrust
  • LangSmith
  • Langfuse
  • Arize Phoenix / AX

Anthropic 的重點是：框架本身並不是最重要的，真正決定 Eval 品質的是 Task 與 Grader 的設計品質。
